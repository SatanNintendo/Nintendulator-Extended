# Аудит плавности скроллинга (MMR) — сессия 1

## Что показали логи (данные, не догадки)
Файл `nintendulator_timing.log` (360 подряд идущих кадров, windowed, MMR ON, OpenGL):
- Из 360 кадров нестабильны ровно 4 (кадры 31, 154, 286, 359): present = 21.0 / 39.7 / 19.2 / 22.9 мс.
  У всех четырёх `tex == pboMap` (4.2 / 22.8 / 2.4 / 7.0 мс) — то есть render-поток блокируется
  **внутри `glMapBuffer`**. Всё остальное (swap, t2b, ofe, drc, pace) в норме.
- После кадра 154 счётчики DWM дают `dwmFrameStep` = 0, затем 2: это и есть реальный пропущенный
  refresh (видимый «срыв» скролла).
- Шапка лога: `Presentation clock: QPC FALLBACK`, `GL vsync verified: NO`, `DwmFlush: compiled OUT`.
  Т.е. кадры подавались по свободному QPC-расписанию с произвольной фазой относительно vblank.

`nintendulator_events.log`:
- Сессии без netplay: все PRESGAP объясняются `tex` (gap ≈ 16.7 + tex), причём `tex` растёт
  с ~5 мс до ~30 мс за 10 минут. Это тот же `glMapBuffer`.
- Netplay-сессия: NETSTALL 20–37 мс **ровно каждые 10.000 с** (exch ≈ каждые 599 кадров).
  Пауза целиком внутри `kailleraModifyPlayValues()`; в коде Kaillera.cpp периодической работы нет,
  периодический дамп в netplay отключён. Источник — вне этого репозитория (kailleraclient.dll /
  сервер / сторона второго игрока). Эмулятор может лишь не усугублять (см. ниже).

## Первопричины
1. **Блокировка загрузки текстуры**: на каждый кадр `glBufferData(NULL)` (orphaning) + `glMapBuffer`
   поверх кольца из 4 PBO. Драйвер периодически ждёт GPU/выделяет память -> 4..30 мс на render-потоке.
2. **Нет привязки к реальному vblank**: кадр уходил в произвольной точке периода, поэтому любая
   задержка превращалась в пропуск composition DWM; плюс два независимых тактовых генератора
   (QPC и дисплей) медленно «плывут» друг относительно друга.

## Что изменено
- `GFX.cpp`: кольцо PBO с **fence** (`ARB_sync`) + `glMapBufferRange(UNSYNCHRONIZED)`; поток выбирает
  свободный PBO опросом fence (timeout 0), ожидание ограничено 6 мс, иначе загрузка кадра
  пропускается (рисуется прежняя текстура). Нужен GL 3.2 / ARB_sync, иначе работает прежний путь.
  Каждый сэмпл `DwmGetCompositionTimingInfo` передаётся в MonitorSync. Новые строки в шапке
  (`Vblank lock`, `PBO fence mode`, `allBusy`, `skippedUploads`) и колонка `vph` в строках.
- `MonitorSync.cpp/.h`: ветка пейсинга **с фазовой автоподстройкой к vblank** (`NotifyVBlankGrid`).
  Период берётся из DWM (`rateRefresh`), цель кадра = vblank + фаза (по умолчанию 3.0 мс),
  ФАПЧ с ограничением ±0.1 мс/кадр, жёсткий ресинк при ошибке > 2 мс, пропуск «устаревших» слотов
  без потери выравнивания. Точное ожидание: таймер до цели−1 мс, затем спин. Если сэмплов нет
  (exclusive fullscreen, мониторы 75/120/144 Гц) — работает прежний QPC-путь без изменений.
- Реестр: `MMRPhaseTenthMs` (DWORD, в 0.1 мс, по умолчанию 30). Больше = больше запас против
  подвисаний, но +1:1 задержка ввода; меньше — наоборот.

## Что проверить в следующем логе (MMR ON, windowed, без netplay)
1. Шапка: `Vblank lock: LOCKED`, `PBO fence mode=1`, `hard resyncs` = 1–2.
2. Колонка `vph` ≈ 3.2–4 мс во всех строках (фаза сдвинута на время загрузки/свопа).
   Если `vph` «гуляет» или стабильно у 14–16 мс — прислать лог, подберём `MMRPhaseTenthMs`.
3. `pboMap` больше не должен давать 4–23 мс; `dwmFrameStep` везде 1; `skippedUploads` = 0.
4. Если `PBO fence mode=0` — драйвер без ARB_sync, включится прежний путь (тогда нужен лог GL_RENDERER).

## Ограничения / честно
- Проверено: статический аудит, компиляция (mingw-w64, GFX/MonitorSync/APU/Nintendulator), модельный
  прогон ФАПЧ (сходимость, шум, дрейф ±300 ppm, подвисания 22/40 мс). **На железе не запускалось.**
- 10-секундный netplay-стопор этим патчем не устраняется (он приходит из lockstep). Видимый эффект
  ограничен одним повтором кадра, фаза после него восстанавливается автоматически.
